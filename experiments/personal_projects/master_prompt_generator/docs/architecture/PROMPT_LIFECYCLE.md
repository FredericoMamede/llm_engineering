# Prompt Lifecycle & Versioning Model

> **Purpose:** Define formal lifecycle states, versioning semantics, and evolution tracking for prompts in the Master Prompt Generator system.

---

## Lifecycle States

### State Machine

```
Draft → Generated → Evaluated → Refined → Approved → Archived
  ↓         ↓            ↓          ↓          ↓
  └─────────┴────────────┴──────────┴──────────┘
         (Can loop back to Refined)
```

### State Definitions

#### 1. **Draft**
- Initial state when prompt is first created
- May be incomplete or untested
- Not yet evaluated
- Can be edited freely

**Transitions:**
- `Draft → Generated`: When prompt is first generated by system

#### 2. **Generated**
- Prompt has been created by the generation engine
- Basic structure is complete
- Not yet evaluated for quality
- Can be edited or evaluated

**Transitions:**
- `Generated → Evaluated`: When quality evaluation is run
- `Generated → Draft`: If user manually edits

#### 3. **Evaluated**
- Quality metrics have been computed
- Score is available (0-10 scale)
- Issues may be identified
- Ready for refinement or approval

**Transitions:**
- `Evaluated → Refined`: If score < threshold or issues found
- `Evaluated → Approved`: If score meets quality threshold
- `Evaluated → Draft`: If major manual changes needed

#### 4. **Refined**
- Prompt has been improved through refinement loop
- New version created from previous
- Re-evaluation recommended
- Parent version tracked

**Transitions:**
- `Refined → Evaluated`: After refinement, re-evaluate
- `Refined → Approved`: If refinement meets quality bar
- `Refined → Draft`: If refinement requires manual intervention

#### 5. **Approved**
- Prompt meets quality standards
- Ready for production use
- Can be exported/shared
- Considered stable version

**Transitions:**
- `Approved → Refined`: If improvements needed later
- `Approved → Archived`: If superseded or deprecated

#### 6. **Archived**
- Prompt is no longer actively used
- Preserved for historical reference
- Cannot be directly edited
- Can be restored if needed

**Transitions:**
- `Archived → Draft`: If restored for new use

## Versioning Semantics

### Version Format

```
MAJOR.MINOR.PATCH
```

**Examples:**
- `1.0.0` - Initial approved version
- `1.1.0` - Minor improvement (better examples)
- `1.1.1` - Patch (typo fix, formatting)
- `2.0.0` - Major change (different technique, structure)

### Versioning Rules

#### **MAJOR** (Breaking Changes)
Increment when:
- Prompt technique changes (zero-shot → few-shot)
- Output format changes (JSON → Markdown)
- Core structure significantly altered
- Model compatibility changes
- Breaking semantic changes

#### **MINOR** (Non-Breaking Improvements)
Increment when:
- Examples added/improved
- Constraints refined
- Wording improved (same meaning)
- Additional context added
- Quality improvements

#### **PATCH** (Fixes)
Increment when:
- Typo corrections
- Formatting fixes
- Minor clarifications
- Token optimization (same output)
- Documentation updates

## Breaking Change Detection

### What Constitutes a Breaking Change

1. **Output Format Change**
   - JSON → Markdown
   - Structured → Unstructured
   - Schema changes

2. **Technique Change**
   - Zero-shot → Few-shot (requires examples)
   - Direct → Chain-of-thought (requires reasoning)
   - Single → Multi-step (requires chaining)

3. **Model Compatibility**
   - Model-specific adaptations that break other models
   - Context window requirements change
   - Token limits exceeded

4. **Semantic Change**
   - Task definition changes
   - Expected output fundamentally different
   - Use case category changes

### Breaking Change Detection Algorithm

```python
def is_breaking_change(old_prompt, new_prompt):
    """
    Detect if change is breaking.
    Returns: (is_breaking: bool, reasons: List[str])
    """
    reasons = []
    
    # Check output format
    if old_prompt.output_format != new_prompt.output_format:
        reasons.append("Output format changed")
    
    # Check technique
    if old_prompt.technique != new_prompt.technique:
        reasons.append("Prompt technique changed")
    
    # Check model compatibility
    if old_prompt.target_models != new_prompt.target_models:
        reasons.append("Model compatibility changed")
    
    # Check semantic similarity (using embeddings)
    similarity = cosine_similarity(
        old_prompt.embedding,
        new_prompt.embedding
    )
    if similarity < 0.7:  # Threshold
        reasons.append("Semantic meaning significantly changed")
    
    return len(reasons) > 0, reasons
```

## Regression Detection

### How Regressions Are Detected

1. **Score Regression**
   - `evaluation_score_after < evaluation_score_before`
   - Threshold: > 0.5 point drop

2. **Metric Regression**
   - Any individual metric drops significantly
   - Threshold: > 1.0 point drop in any metric

3. **Anti-Pattern Introduction**
   - New anti-patterns detected in refined version
   - Previously clean prompt now has issues

4. **Cost Regression**
   - Token count increases without quality improvement
   - Cost per run increases > 20%

### Regression Response

When regression detected:
1. **Alert user** with specific metrics
2. **Suggest rollback** to previous version
3. **Identify cause** of regression
4. **Block approval** until resolved

## Safe Evolution Patterns

### Pattern 1: Incremental Refinement
```
v1.0.0 (score: 7.5) → v1.1.0 (score: 8.0) → v1.2.0 (score: 8.5)
```
- Small, focused improvements
- Each version improves score
- No breaking changes

### Pattern 2: Experimental Branching
```
v1.0.0 (approved)
  ├── v2.0.0-alpha (experimental: different technique)
  └── v1.1.0 (safe improvement)
```
- Try major changes in parallel
- Keep stable version available
- Compare before merging

### Pattern 3: Model-Specific Variants
```
v1.0.0 (generic)
  ├── v1.0.0-claude (Claude-optimized)
  ├── v1.0.0-gpt4 (GPT-4-optimized)
  └── v1.0.0-llama (Llama-optimized)
```
- Same base prompt
- Model-specific adaptations
- Tracked as variants, not versions

## Implementation Notes

### Database Schema

```sql
CREATE TABLE prompts (
    id UUID PRIMARY KEY,
    version VARCHAR(20) NOT NULL,
    parent_prompt_id UUID REFERENCES prompts(id),
    lifecycle_state VARCHAR(20) NOT NULL,
    
    system_prompt TEXT,
    user_prompt TEXT NOT NULL,
    
    use_case VARCHAR(100),
    category VARCHAR(50),
    complexity_tier INTEGER,
    target_model VARCHAR(50),
    
    change_reason TEXT,
    evaluation_score_before FLOAT,
    evaluation_score_after FLOAT,
    evaluation_delta FLOAT,
    
    estimated_input_tokens INTEGER,
    estimated_output_tokens INTEGER,
    
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    approved_at TIMESTAMP,
    archived_at TIMESTAMP,
    
    author VARCHAR(20),
    generated_by VARCHAR(50),
    
    metadata JSONB  -- Flexible storage for additional fields
);

CREATE INDEX idx_prompts_parent ON prompts(parent_prompt_id);
CREATE INDEX idx_prompts_state ON prompts(lifecycle_state);
CREATE INDEX idx_prompts_version ON prompts(version);
```

## Best Practices

1. **Always track parent** when creating new version
2. **Document change reason** for every version
3. **Evaluate before approving** - never skip evaluation
4. **Detect regressions** automatically and alert
5. **Maintain version history** for audit trail
6. **Use semantic versioning** consistently
7. **Archive, don't delete** - preserve history
